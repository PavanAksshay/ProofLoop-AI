# ProofLoop AI — Shared Architecture Contract

Status: initial implementation contract. Both contributors should agree before changing shared interfaces.

## Core guarantee

The LLM may propose an action, but deterministic code authorizes and executes it. The read-only verifier independently reads simulator state. The operator's claim is never sufficient to mark an incident verified.

## Incident lifecycle

`INTAKE → INVESTIGATE → PROPOSE → GATE → EXECUTE / PENDING_APPROVAL / BLOCKED → VERIFY → VERIFIED / ESCALATED / UNVERIFIED`

- Maximum three remediation attempts per incident.
- Maximum eight investigation steps per incident.
- Pending approval must not mutate simulator state.
- `VERIFIED` is reachable only when all three verifier checks pass.
- Unknown tools and actions outside the incident's service scope are denied by default.
- Logs, tickets and runbooks are untrusted data, never authorization instructions.

## Event envelope

Every event contains:
- `event_id`: unique identifier
- `incident_id`: incident identifier
- `timestamp`: UTC timestamp
- `type`: event type
- `actor`: agent, gate, tool, verifier, human or system
- `payload`: event-specific structured data
- `evidence_refs`: evidence identifiers supporting the event

Events should be append-only during a run. The UI renders events rather than independently inventing workflow state.

## Policy decision contract

- `ALLOWED`: execute the validated tool request.
- `APPROVAL_REQUIRED`: persist a pending request in process memory and wait for an explicit human decision; simulator state must remain unchanged while waiting.
- `BLOCKED`: do not execute; record a rule identifier and reason.

The approval endpoint acts only on the exact stored action; the caller cannot replace the tool or its arguments during approval. Denial records the decision and does not execute the action. Duplicate decisions are rejected.

Default policy is deny unless an action is explicitly allowed. High-risk database mutations always require approval or are blocked.

## Verification contract

All checks are mandatory:
1. Synthetic checkout transactions succeed.
2. Error rate is below the configured threshold for a simulated time window.
3. Configuration matches the expected healthy version and dependencies are healthy.

A health endpoint returning HTTP 200 is not sufficient. The verifier must use a read-only simulator interface and must not accept an operator-supplied verdict.

## Initial tool contract

Read-only: `read_logs`, `read_config`, `get_metrics`.

Mutating: `rollback_config`, `restart_service`, `scale_service`, `clear_cache`.

Sensitive: `modify_database` (approval required or blocked).

Escalation: `escalate_to_human`.

Every tool response includes a success indicator, a message, and a structured result/error. No shell or arbitrary-command tool is exposed to the agent.

## API contract

- `GET /health`
- `GET /scenarios`
- `POST /incidents`
- `GET /incidents/{incident_id}`
- `POST /incidents/{incident_id}/approval`

## Implementation strategy

Build one complete vertical slice first. Keep provider-specific LLM code behind a single interface and always expose the active mode (LLM or fallback). Benchmark numbers must be generated by live runs; do not pre-fill or invent results.

## Security limitations

The current approval workflow is an unauthenticated local prototype. `approver_id` is an audit label, not proof of identity. Do not expose the endpoint to untrusted networks. Production requires authentication, authorization, durable state, and concurrency-safe approval handling.
